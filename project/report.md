Проект посвящен построению ML-сервиса, который по табличным признакам клиента оценивает вероятность его оттока. Итоговый результат - воспроизводимый пайплайн обучения и REST API, где endpoint `/predict` использует сохраненную модель, а не заглушку. Проект демонстрирует работу с данными, препроцессингом, baseline, улучшенной моделью, конфигурациями, артефактами, тестами и базовой наблюдаемостью.

## 2. Постановка задачи

Предметная область - удержание клиентов подписочного сервиса. Потенциальный пользователь решения - аналитик или менеджер по клиентскому опыту, которому нужно быстро выделить клиентов с высоким риском ухода и передать их в сценарий удержания.

В терминах ML решается задача бинарной классификации. На вход подаются признаки клиента: возраст, срок пользования сервисом, размер платежа, обращения в поддержку, просрочки, тип договора, автоплатеж, использование мобильного приложения и оценка удовлетворенности. Выход модели - вероятность `churn_probability` и бинарный прогноз `churn_prediction`.

Основные требования к модели:

- интерпретируемый набор входных признаков;
- быстрый инференс для API;
- не только высокая accuracy, но и достаточный `recall` по классу оттока, потому что пропустить клиента с высоким риском хуже, чем отправить часть лишних клиентов на ручную проверку.

Целевые метрики:

- `accuracy` - общая доля верных прогнозов;
- `precision` - насколько точны срабатывания по оттоку;
- `recall` - какая доля клиентов с оттоком найдена моделью;
- `f1` - баланс precision и recall;
- `roc_auc` - качество ранжирования клиентов по риску.

## 3. Данные

В проекте используются синтетические обезличенные данные, сгенерированные в `src/data.py`. Такой выбор безопасен для учебного проекта: в репозитории нет персональных данных, секретов или закрытых выгрузок. Генерация детерминирована через `random_state=42`, поэтому результат воспроизводится.

Файлы данных:

- `data/churn_train.csv` - основная выборка на 1200 строк;
- `data/churn_sample.csv` - первые 20 строк для быстрой демонстрации структуры.

Структура данных:

| Колонка | Тип | Описание |
|---|---|---|
| `age` | числовой | возраст клиента |
| `tenure_months` | числовой | длительность использования сервиса |
| `monthly_spend` | числовой | ежемесячные расходы |
| `support_tickets` | числовой | обращения в поддержку |
| `late_payments` | числовой | просрочки платежа |
| `contract_type` | категориальный | тип договора |
| `has_autopay` | бинарный | подключен ли автоплатеж |
| `uses_mobile_app` | бинарный | используется ли мобильное приложение |
| `satisfaction_score` | числовой | удовлетворенность от 1 до 10 |
| `churn` | бинарный | целевая переменная |

Логика генерации целевой переменной отражает реалистичные зависимости: риск оттока выше при помесячном договоре, большом количестве обращений в поддержку, просрочках, низкой удовлетворенности и малом сроке пользования сервисом. Перед обучением числовые признаки стандартизируются, а категориальный признак `contract_type` кодируется через OneHotEncoder.

Основные шаги EDA и экспериментов описаны в `notebooks/01_eda_and_experiments.ipynb`. Боевой код вынесен в модули `src/`, чтобы проект не зависел от ручного запуска ячеек ноутбука.

## 4. Модели и подходы

В качестве baseline использована `LogisticRegression`. Это простая линейная модель, которая хорошо подходит как стартовая точка: быстро обучается, дает вероятности и показывает, насколько задачу можно решить без сложных нелинейных зависимостей.

В качестве улучшенной модели использован `RandomForestClassifier`. Он устойчив к нелинейным связям, может учитывать взаимодействия признаков и обычно хорошо работает на табличных данных среднего размера. Для задачи оттока это полезно, потому что риск может зависеть от сочетаний факторов: например, короткий срок пользования плюс помесячный договор плюс низкая удовлетворенность.

Пайплайн построен через `sklearn.pipeline.Pipeline`:

```text
CSV/JSON features
  -> pandas DataFrame
  -> ColumnTransformer(StandardScaler + OneHotEncoder)
  -> sklearn classifier
  -> probability, class, risk level
```

Гиперпараметры и пути вынесены в `configs/config.yaml`. Финальная модель сохраняется в `artifacts/churn_model.joblib`.

## 5. Экспериментальный протокол и результаты

Выборка делится на train/test в пропорции 80/20 со стратификацией по целевой переменной. Метрики считаются на тестовой части, которая не используется при обучении.

Результаты из `artifacts/metrics.json`:

| Модель | Accuracy | Precision | Recall | F1 | ROC-AUC | Комментарий |
|---|---:|---:|---:|---:|---:|---|
| LogisticRegression | 0.7917 | 0.6744 | 0.4462 | 0.5370 | 0.7956 | Хороший baseline, выше accuracy и precision |
| RandomForestClassifier | 0.7542 | 0.5429 | 0.5846 | 0.5630 | 0.7864 | Финальная модель, лучше recall и F1 |

Финальной выбрана `RandomForestClassifier`. Хотя baseline немного лучше по accuracy и ROC-AUC, Random Forest лучше находит клиентов с оттоком: `recall=0.5846` против `0.4462`, а `f1=0.5630` против `0.5370`. Для бизнес-сценария удержания это разумный компромисс: важнее не пропустить рисковых клиентов, чем максимизировать общую долю верных ответов.

## 6. Архитектура решения и сервис

Основные компоненты:

- `src/data.py` - генерация и загрузка синтетической выборки;
- `src/model.py` - построение preprocessing pipeline, обучение, оценка и загрузка модели;
- `src/train.py` - точка входа для обучения и сохранения артефактов;
- `src/service.py` - FastAPI-приложение для инференса.

API:

- `GET /health` проверяет, что сервис поднят и модель загружается.
- `POST /predict` принимает JSON с признаками клиента и возвращает вероятность оттока, бинарный прогноз, уровень риска и имя модели.

Пример ответа `/predict`:

```json
{
  "churn_probability": 0.7362,
  "churn_prediction": 1,
  "risk_level": "high",
  "model": "random_forest"
}
```

Технологический стек:

- Python;
- pandas и numpy для данных;
- scikit-learn для ML-пайплайна;
- joblib для сериализации модели;
- FastAPI, Pydantic и Uvicorn для сервиса;
- PyYAML для конфигураций;
- pytest для тестов.

## 7. Наблюдаемость, конфигурация и безопасность

В сервисе включено базовое логирование через стандартный модуль `logging`: при запросе к `/predict` логируется вероятность и уровень риска. Endpoint `/health` служит простой проверкой работоспособности сервиса и доступности модели.

Конфигурация вынесена в `configs/config.yaml`: там задаются пути к данным и артефактам, размер выборки, test split, параметры моделей и порт сервиса. В `configs/.env.example` перечислены переменные окружения `APP_ENV`, `LOG_LEVEL`, `MODEL_PATH`, `CONFIG_PATH`; реальные `.env` и секреты в проекте не используются.

Безопасность данных обеспечивается тем, что весь датасет синтетический. В репозитории нет персональных данных, паролей, токенов или закрытых ключей.

## 8. Ограничения и дальнейшая работа

Главное ограничение - синтетический датасет. Он показывает инженерный пайплайн и корректность сервиса, но не заменяет полноценной проверки на реальных или открытых исторических данных. Также в проекте пока нет Dockerfile, авторизации, хранения истории запросов и мониторинга drift-а.

Дальнейшее развитие:

- обучить модель на реальном обезличенном датасете;
- добавить подбор гиперпараметров и кросс-валидацию;
- добавить интерпретацию признаков через permutation importance или SHAP;
- добавить Dockerfile и CI;
- сохранять входные запросы и ответы модели для аудита;
- добавить мониторинг качества и распределения признаков.
